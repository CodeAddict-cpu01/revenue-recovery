🎯 Core Objective

The system is built around one principle:

Don't just identify failed payments. Recover revenue safely, measurably,
and with accountability.

The agent closes the loop from:
Failure
   ↓
Understanding
   ↓
Decision
   ↓
Policy
   ↓
Execution
   ↓
Verification
   ↓
Measurement

🛡️ Recovery Policy Engine

AI recommendations are not executed blindly.

Every recommendation passes through a deterministic policy layer.

The policy engine evaluates:

AI Recommendation
       │
       ▼
Is the action allowed?
       │
       ▼
Has the attempt limit been reached?
       │
       ▼
Has recovery already succeeded?
       │
       ▼
Is recovery still permitted?
Current Recovery Limit
Maximum Recovery Attempts = 1

This provides a clear stopping rule.

If the policy rejects recovery:

FAILED
  │
  ▼
POLICY CHECK
  │
  ▼
STOPPED

This prevents uncontrolled retry loops.

💳 Razorpay Recovery Execution

When recovery is approved, the system creates a new Razorpay recovery order.

Failed Payment
      │
      ▼
Policy Approved
      │
      ▼
Create Recovery Order
      │
      ▼
Razorpay Checkout
      │
      ▼
Customer Completes Payment

The original payment remains traceable through the recovery order and recovery
payment identifiers.

🔐 Secure Recovery Verification

A checkout being opened does not mean revenue was recovered.

The backend verifies the Razorpay payment signature.

Recovery Payment
       │
       ▼
Signature Verification
       │
   ┌───┴────┐
   │        │
 VALID    INVALID
   │        │
   ▼        ▼
RECOVERED  REJECTED

Only after successful backend verification is the original failed payment
marked:

RECOVERED

🔂 Duplicate Webhook Protection

Payment systems can receive repeated webhook events.

Revenue Recovery protects against duplicate processing.

Example:

RAZORPAY WEBHOOK RECEIVED

Payment already exists

DUPLICATE WEBHOOK

Skipping AI analysis.

This prevents the same payment failure from triggering duplicate AI decisions
or duplicate processing.

📈 Expected Recovery

The system estimates expected recovery using:

Expected Recovery
=
Payment Amount × AI Recovery Probability

Example:

Failed Payment = ₹500

AI Probability = 70%

Expected Recovery
= ₹500 × 70%
= ₹350

Across a batch:

Expected Recovery
=
Σ (Payment Amount × Recovery Probability)

This allows the merchant to estimate the potential value of the recovery
pipeline.

⚠️ Real Revenue vs Simulation

Revenue Recovery deliberately distinguishes between real recovery and
simulation results.

Real Recovery

A real Razorpay Test Mode payment is completed and its signature is verified.

RECOVERY_VERIFIED
       ↓
RECOVERED
Simulation

Synthetic payment failures are evaluated to estimate system performance.

SIMULATED RECOVERED REVENUE

Simulation results are not presented as real merchant revenue.

Prerequisites

Install:

Java 17+
Maven
Ollama
Razorpay Test Mode account

1. Clone the Repository
git clone YOUR_GITHUB_REPOSITORY_URL
cd revenue-recovery

2. Start Ollama

Pull the required model:

ollama pull llama3.2:3b

Start Ollama:

ollama serve

The application expects Ollama at:

http://localhost:11434

Create:

src/main/resources/application-local.properties

Add:

razorpay.key.id=YOUR_RAZORPAY_KEY_ID
razorpay.key.secret=YOUR_RAZORPAY_SECRET
razorpay.webhook.secret=YOUR_RAZORPAY_WEBHOOK_SECRET
Security

Never commit:

application-local.properties

Never commit:

Razorpay secret keys
Webhook secrets
API keys
Database files

The repository's .gitignore is configured to keep local secrets and generated
data out of Git.

▶️ Run the Application

Start Spring Boot:

mvn spring-boot:run

The application runs at:

http://localhost:8080

Open the dashboard:

http://localhost:8080

For local development, expose the application using a tunnel such as
Cloudflare Tunnel.

/api/webhooks/razorpay

payment.failed

🧪 Batch Simulation API

Run a simulation using:

POST /api/simulation/run?count=100

Example:

curl -X POST \
  "http://localhost:8080/api/simulation/run?count=100"

The simulation supports a bounded batch size and does not create real Razorpay
payments.

🛡️ Safety Model

Revenue Recovery uses multiple control layers.

Layer 1 — AI Constraints

The AI operates within predefined failure types and actions.

Layer 2 — Deterministic Policy

AI recommendations must pass the policy engine.

Layer 3 — Bounded Attempts

Recovery attempts are limited.

Layer 4 — Backend Verification

Successful recovery requires Razorpay signature verification.

Layer 5 — Auditability

Recovery events are persisted in an audit trail.

Layer 6 — Duplicate Protection

Repeated webhook events do not trigger duplicate processing.
